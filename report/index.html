🔑 Key Finding: Understanding Per-Call vs Whole Application Overhead

eBPF uprobe overhead is approximately ~5 microseconds per function call, regardless of function duration.

Per-Call Overhead (Individual Function):

  • For nanosecond functions: Overhead appears catastrophic (1000x+)
  • For microsecond functions: Overhead is moderate (1-10x)
  • For millisecond functions: Overhead is negligible (<1%)

Whole Application Overhead (Total Execution Time):

  • This is what matters in production!
  • Measured as the increase in total wall clock time
  • Includes all traced calls plus application overhead
  • Typically much lower than per-call overhead averages

bpftime (Userspace eBPF): bpftime runs eBPF programs in userspace, avoiding kernel context switches. This can significantly reduce per-call overhead compared to kernel eBPF uprobes, especially for high-frequency function calls.

Conclusion: eBPF and bpftime are both excellent for GPU tracing where HIP API calls typically take 10-1000 μs! The whole application overhead is typically <5% for realistic workloads. bpftime may offer even lower overhead by staying in userspace.

GPU/HIP Tracing Recommendation

For GPU and HIP API tracing, eBPF is highly recommended because:

  • HIP API calls typically take 10-1000 μs (much slower than uprobe overhead)
  • Slow API calls can take milliseconds (making tracer overhead negligible)
  • No application modification required (zero code changes)
  • Can trace at kernel/driver boundary for complete visibility
  • Expected total application overhead: <1%

Conclusion

  • All 4 options achieve 0 ns hot-path overhead when no controller is attached — late-load design works as specified.
  • Attach latency 2-3 ms across all options, dominated by dlopen + SDK initialize, not the IPC channel.
  • No sudo, no capabilities, no specific kernel version required for any option.
  • Recommended for production: Option F+memfd (strongest security with zero filesystem footprint).
