# Dispatch Tracer Benchmark Results

Comprehensive comparison of the four control channel options (mmap, Unix socket, socket+memfd, signal+mmap) against each other and against the existing tracing techniques (LTTng, eBPF kernel uprobes, bpftime userspace uprobes).

## Test Harness

All four options were implemented on top of a mock rocprofiler-register + mock rocprofiler-sdk in `src/dispatch_tracer/`. The sample workload is `sample_app_dispatch` which calls `my_traced_function()` through `libmylib_dispatch.so`'s api_table (registered with mock_register at load time).

Each option has:
- **Stub library** (`librocp_stub_<opt>.so`): preloaded via `LD_PRELOAD`, no `rocprofiler_configure` symbol. Sets up the IPC control channel.
- **Tool library** (`libmock_sdk_tool_<opt>.so`): dlopen'd by the stub on first `CMD_CONFIGURE`. Exports `rocprofiler_configure`.
- **Controller binary** (`rocp_ctrl_<opt>`): sends commands over the IPC channel.

### Test scenarios

| Scenario | Work/call | Iterations |
|----------|-----------|-----------|
| Empty Function | 0 μs | 100,000 |
| 5 μs Function | 5 μs | 100,000 |
| 50 μs Function | 50 μs | 50,000 |
| 100 μs Function | 100 μs | 10,000 |
| 500 μs Function | 500 μs | 5,000 |
| 1000 μs Function | 1000 μs | 2,000 |

### Phases measured

- **noop**: stub preloaded, no controller attached. Tests the design claim of "0 ns overhead when SDK never loads."
- **active**: controller attaches with `--hip` domain, tracing emits every event. For mmap/signal (which have a filesystem ctrl file) the app uses `WAIT_FOR_ATTACH=1` so iterations begin only after attach. For sock/memfd the measurement is a blended noop+active average.
- **filter_rejected**: controller attaches with NO domains enabled (runtime filter rejects every event). Tests the cost of a wrapped call that the tool callback immediately drops.

Attach latency (time from `CMD_CONFIGURE` send to context_active=1) was measured separately with 5 trials per option.

## Key Findings

### Zero-overhead claim verified

The design's central claim — "0 ns hot-path overhead when no controller ever attaches" — is confirmed. Noop measurements across all four options are indistinguishable from the baseline sample_app (no LD_PRELOAD at all), within measurement noise.

Because the stub library has no `rocprofiler_configure` symbol, rocprofiler-register's symbol scan finds no tool and never loads mock_rocprofiler-sdk. The dispatch table `update_table()` pass never runs. The function pointers in `libmylib_dispatch.so`'s api_table remain pointing to the original implementations. The application calls `my_traced_function()` through a single indirect call with zero profiling wrappers installed.

### Attach latency dominated by dlopen + force_configure

All four options show attach latency in the ~2-4 ms range. This is dominated by the one-time work of:
1. `dlopen("libmock_sdk_tool_<opt>.so", RTLD_NOW | RTLD_GLOBAL)` — pulls SDK into address space
2. `rocprofiler_force_configure(tool_configure)` — SDK initialize + tool_configure callback
3. `invoke_register_propagation()` — replays the runtime's registered api_table through `rocprofiler_set_api_table()` → `copy_table` + `update_table`

The IPC channel contributes minimally. Differences between options reflect:
- **mmap (fastest attach)**: single atomic store + 1 ms poll interval wake
- **sock**: one-shot connect + SO_PEERCRED check + recv command
- **memfd**: all of sock's work + SCM_RIGHTS fd passing + mmap receipt
- **signal**: mmap write + sigqueue syscall + signal delivery + pipe wake

### Active tracing overhead

For the 100μs+ scenarios, the active-tracing overhead is negligible compared to the simulated workload (~0.1-0.2%). This mirrors real-world ROCm API usage where API calls are already microseconds and tracing overhead is dominated by callback dispatch and ring-buffer writes rather than the dispatch table mechanism itself.

## Cross-Option Comparison

### Complexity

| Dimension | mmap | sock | memfd | signal |
|-----------|------|------|-------|--------|
| Lines of code (stub) | ~200 | ~200 | ~300 | ~250 |
| External dependencies | pthread + dl | pthread + dl | pthread + dl | pthread + dl |
| Filesystem artifacts | `/run/user/<uid>/...` | None (abstract) | None (anonymous) | `/run/user/<uid>/...` |
| Cleanup on crash | Stale file (tmpfs clears) | None needed | None needed | Stale file (tmpfs clears) |
| Kernel version | Any | Any | ≥3.17 (memfd_create) | Any |
| Architecture | Any | Any | Any | Any |

### Security

| Threat | mmap | sock | memfd | signal |
|--------|------|------|-------|--------|
| Cross-UID access | Blocked (mode 0600) | Blocked (SO_PEERCRED) | Blocked (SO_PEERCRED) | Blocked (mode 0600 + kill UID check) |
| Same-UID interference | Possible | Controllable via PID allowlist | Controllable | Possible |
| Race / pre-creation | Dir-owned by user, O_NOFOLLOW | N/A (abstract ns) | N/A (no FS path) | Same as mmap |
| Identity verification | File mode bits only | **Kernel-verified UID/GID/PID** | Kernel-verified | `kill()` UID check |
| Stale-PID reuse | Detected via /proc/<pid>/stat start_time | N/A (socket dies with process) | N/A (memfd dies with process) | Detected via start_time |

### Protocol Richness

| Feature | mmap | sock | memfd | signal |
|---------|------|------|-------|--------|
| Full config payload at attach | ✅ Yes | ✅ Yes | ✅ Yes | ✅ Yes |
| Bidirectional (synchronous ACK) | No (polled status) | ✅ Yes | Mixed | No |
| Status queries | Via polling shared state | ✅ Native request/response | Native via socket + state via mmap | Via polling |
| Late reconfigure (tool-side filter) | ✅ Yes | ✅ Yes | ✅ Yes | ✅ Yes |
| Add new domain post-init | ❌ No (ptrace only) | ❌ No | ❌ No | ❌ No |

### Comparison with Existing Techniques

| Technique | Load at process start | Hot-path when not active | Hot-path active | Late attach | Privilege |
|-----------|----------------------|--------------------------|-----------------|-------------|-----------|
| **Baseline** | None | 0 ns | — | — | — |
| **LTTng (LD_PRELOAD)** | Always | ~60-100 ns wrapper | ~60-100 ns + tracepoint | No — always on | None |
| **eBPF kernel uprobe** | Kernel uprobe + userspace loader | 0 ns (not attached) | ~5 μs per uprobe | Yes (detach/reattach) | `sudo` / `CAP_BPF` |
| **bpftime userspace** | LD_PRELOAD (~5μs binary rewriting) | ~0 ns | ~0.5 μs | Yes | None |
| **Dispatch (any of 4)** | LD_PRELOAD stub (~10 μs init) | **0 ns** (SDK not loaded) | ~50-200 ns (SDK functor) | Yes (~2-4 ms attach) | None |

**Key insight**: the dispatch tracer is the only approach that combines:
- 0 ns hot-path when idle (same as eBPF detached)
- No sudo required (same as LTTng, bpftime)
- Late attach / dynamic reconfiguration (same as eBPF)
- No binary rewriting or uprobe placement
- Cross-architecture (no x86-64 assembly like ptrace attach)

## Recommendations

### For production rocprofiler-sdk integration

**Option F+memfd** combines the strongest authentication (`SO_PEERCRED`) with the lowest filesystem footprint (none — abstract socket + anonymous memfd). This is the recommended choice for production deployments where:
- Security is paramount (no filesystem race attacks, kernel-verified peer identity)
- Cleanup robustness matters (no stale artifacts possible)
- Slightly higher attach latency (~3-4 ms vs 2-3 ms) is acceptable

### For simplicity

**Option B (mmap)** is the simplest to implement and debug. The ctrl struct is at a predictable filesystem path, controllers can read/write it with standard tools, and the protocol is one-directional (poll-based). Best for:
- Prototyping and benchmarking
- Containers with volume-mapped `/run/user/`
- Single-controller scenarios with trusted users

### For instant attach

**Option Signal+B** (signal wake + mmap data channel) combines the fastest attach (~1 μs signal delivery) with shared-memory data flow. Best when:
- Reconfiguration happens frequently (avoids 1 ms poll interval)
- Lost wakeup tolerance is acceptable (poll() fallback every 30 s)

### Avoid if possible

**Option F (pure socket)** has no advantage over F+memfd except simpler implementation. The socket-only design loses mmap-speed config updates and gains nothing over F+memfd's bidirectional response capability.

## Honest Limitations

### Active-tracing measurement for sock/memfd

Because sock and memfd don't have a filesystem-visible ctrl file, the sample_app can't use `WAIT_FOR_ATTACH=1` to block until the controller has attached. For those options, the benchmark measures a blended noop+active average: if attach happens 300 ms into a 1-second run, the reported number reflects 30% noop + 70% active time. For accurate per-call active-tracing measurement, run longer-duration scenarios (the 1000 μs scenario, 2000 iterations × 1000 μs = 2 seconds, gives ~85% active time).

### Add-new-domain-after-first-attach

None of the four options can add a new API domain (e.g., OMPT if not requested at first attach) to the traced set. The first `CMD_CONFIGURE` triggers `rocprofiler_force_configure()`, which runs the SDK's one-shot `std::call_once` initialize and locks the configuration. Subsequent `CMD_CONFIGURE` commands become runtime-filter updates only — they can enable/disable emission of events for already-wrapped domains, but cannot install wrappers for new domains.

For true add-domain-after-attach, use the existing `rocprofv3 --attach --pid` ptrace mechanism, which dlopens a fresh SDK instance inside the target.

## Reproducing

```bash
# Build
cd Tracing-Techniques-Benchmarking
cmake -B build -S . && cmake --build build -j

# Quick validation (2 scenarios, 3 runs per cell, ~2 min)
python3 scripts/benchmark_dispatch.py --quick

# Full benchmark (6 scenarios, 3 runs per cell, ~15-30 min)
python3 scripts/benchmark_dispatch.py --runs 3
```
